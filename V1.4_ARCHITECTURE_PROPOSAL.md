## 2. PROPOSED NEW MODULE SPECIFICATIONS

### Module 1: `services/reasoning_service.py` (Multi-Hop Iterative Retriever)
- **Responsibility**: Decomposes complex comparative or multi-step questions into sequential or parallel sub-queries, executes targeted retrieval for each sub-query, and compiles an integrated evidence graph.
- **Key Functions**:
  - `decompose_query(query: str, doc_summaries: List[str]) -> List[SubQuery]`
  - `execute_iterative_retrieval(subqueries: List[SubQuery], user_id: int, filenames: List[str], max_hops: int = 3) -> MultiHopEvidence`
  - `evaluate_hop_sufficiency(current_evidence: List[DocumentChunk], original_query: str) -> bool`
- **Security Boundary**: Every sub-query retrieval call strictly inherits the validated `user_id` and document ownership constraints. Sub-queries cannot access unowned documents.
- **Fail-Safe Mechanism**: Hard bounded iterations ($hops \le 3$, execution timeout $\le 4.0\text{s}$) with fallback to standard hybrid single-pass retrieval if decomposition fails.

---

### Module 2: `services/verification_service.py` (Evidence Verification & Conflict Detector)
- **Responsibility**: Analyzes retrieved candidate chunks across multiple documents to identify factual discrepancies (e.g. opposing numbers, differing dates, contradictory assertions) and verify if the evidence sufficiently covers the user prompt.
- **Key Functions**:
  - `detect_cross_document_conflicts(chunks: List[DocumentChunk]) -> List[EvidenceConflict]`
  - `verify_evidence_sufficiency(query: str, chunks: List[DocumentChunk]) -> SufficiencyReport`
  - `format_conflict_grounding_xml(chunks: List[DocumentChunk], conflicts: List[EvidenceConflict]) -> str`
- **Output Format**:
  ```xml
  <evidence_pool sufficiency="sufficient" conflict_detected="true">
    <retrieved_document id="1" filename="Q1_Report.pdf" page="4">
      Revenue in 2025 reached $12M.
    </retrieved_document>
    <retrieved_document id="2" filename="Q2_Update.pdf" page="2">
      Revised revenue in 2025 was adjusted to $10.5M.
    </retrieved_document>
    <conflict_annotation claim_a="Revenue $12M" source_a="[1]" claim_b="Adjusted revenue $10.5M" source_b="[2]" attribute="revision" />
  </evidence_pool>
  ```
- **Security Boundary**: Pure in-memory analysis of authorized chunk payloads. No stateful side effects.

---

### Module 3: `services/table_extractor.py` (Table-Aware Structured Chunking)
- **Responsibility**: Ingests tabular data from XLSX, CSV, DOCX, and PDF tables, preserving column-header and row-context relationships so that individual cell values retain their semantic meaning inside vector chunks.
- **Key Functions**:
  - `extract_structured_table_chunks(sheet_data, filename: str) -> List[TableChunk]`
  - `serialize_table_row_with_headers(row_values, header_hierarchy) -> str`
- **Chunk Format**:
  ```text
  [Table: Q3 Financial Summary | Sheet: BalanceSheet]
  Row: Operating Expenses | Category: R&D | Q1: $1.2M | Q2: $1.4M | Q3: $1.5M | YoY Growth: +12%
  ```

## 3. API ROUTE & BACKWARD COMPATIBILITY PRESERVATION

The v1.4.0 evolution will strictly preserve the existing 35 API routes in `routers/`.

### Extended (Non-Breaking) Schemas:
In `schemas/chat_schemas.py`:
- `ChatRequest` gains optional fields:
  - `enable_multihop: bool = True`
  - `detect_conflicts: bool = True`
- `ChatResponse` / SSE metadata events gain optional fields:
  - `hops_executed: int`
  - `conflicts_detected: List[Dict[str, Any]]`
  - `sufficiency_status: str` (e.g., `"sufficient"`, `"partial"`, `"insufficient"`)

If a client sends standard v1.3.0 requests, default settings preserve full v1.3.0 output structure while transparently benefiting from improved accuracy.
